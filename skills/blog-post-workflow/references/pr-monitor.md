# PR-comment monitor routine

Self-contained routine the blog-post-workflow PR-monitor cron runs while a post's PR is open — every ~15 minutes at first, backing off to 30 and then 60 minutes when the PR sits idle, and snapping back to 15 on any reviewer activity (§Adaptive cadence below). Driven entirely by `{drafts_dir}/<slug>/pr-monitor.json` + the live PR, so a cron firing in a fresh session needs no prior context. Read the state file first; everything else derives from it (`repo`, `worktree`, `branch`, `pr_number`, `mode`, and — when the active publish adapter is `wordpress-rest` — `wp_post_id`).

## Each firing

1. Read `{drafts_dir}/<slug>/pr-monitor.json` (`status`, `worktree`, `branch`, `pr_number`, `repo`). If `status` is `done` / `closed`, `CronDelete` this cron and exit (self-heal). `approved` is NON-terminal: the review was recorded and is being HELD (step 5 below), so keep monitoring exactly like `open`. Otherwise resolve the worktree: if the `worktree` path no longer exists on disk, recreate it from the branch, falling back to the remote branch if the local branch is also gone: `git worktree add "$worktree" "$branch" 2>/dev/null || { git fetch origin "$branch" && git worktree add "$worktree" -b "$branch" "origin/$branch"; }`. **All branch commits/pushes in this routine run via `git -C "$worktree"`, and all post-file edits target paths under `$worktree/`, so the operator's working branch is never touched.**
2a. **Layout check, per commit (`astro-git-pr` with `publish.astro.preview_comment_marker` set).** `HEAD=$(gh pr view <pr_number> -R <repo> --json headRefOid -q .headRefOid)`. Skip when the state file's `layout_check.commit` equals `$HEAD` (already measured for this push). Otherwise find the CI comment carrying the marker and read its `updated_at` (`gh api repos/<repo>/issues/<pr_number>/comments --jq '.[] | select(.body | contains("<marker>")) | .updated_at'`); skip, and try again next firing, when there is no such comment or its `updated_at` is earlier than `$HEAD`'s commit date (`gh api repos/<repo>/commits/$HEAD --jq .commit.committer.date`): the preview still shows the previous push. Then run `node "${CLAUDE_PLUGIN_ROOT}/adapters/publish/scripts/layout-check.mjs" --url "<staging url>"`, apply the §Staging step 9 reading of the JSON (`finalUrl`/`title` guard), and write `layout_check: { "commit": "$HEAD", "result": "pass" | "<n> finding(s): <one line each>" | "not checked (<why>)" }` to `pr-monitor.json`. On findings, post ONE PR comment with the finding lines and what to change, carrying the marker `<!-- handled:layout:$HEAD -->`, under the same at-most-once rule as every other monitor comment (step 3 below): check the PR for that exact marker first and never post when it is already there; the marker is keyed by commit, so the local record is only a cache and a crash between posting and writing it cannot duplicate or lose the comment. A new push gets a new `$HEAD`, a new measurement and, when needed, a new comment.

2. **External-publish check (`wordpress-rest` only, when the state file carries `wp_post_id`).** `GET {base_url}/wp-json/wp/v2/posts/<wp_post_id>?_fields=status` (`base_url` from `publish.wordpress.base_url`) — a normal authenticated call by the already-recorded ID, **not a probe**: the probe-once rule governs only the one-shot credential-verification call at the adapter's §Staging step 2; a routine status read by a stored ID is safe and expected to run on every firing.
   - **`status: publish`** → the human already clicked Publish in wp-admin. Treat this exactly as a Gate 2 approval: run the finalize-on-approval sequence (`${CLAUDE_PLUGIN_ROOT}/skills/blog-post-workflow/SKILL.md` Step 15.3 PR path, which dispatches to `adapters/publish/wordpress-rest.md` `## On Gate 2 approval`), with the one difference that section's own step 1 already encodes — the final content sync is SKIPPED because the live post is now authoritative — then `CronDelete` and exit. **This precedence is deliberate:** exiting here means step 3's comment poll never runs this firing, so any PR comments still awaiting a reply are left un-replied — the human's decision to publish overrides addressing pending feedback, and the final report should say so explicitly rather than implying every comment was handled.
   - **`status` is anything else** (normally `draft`) → not a signal; continue to step 3 below as usual.
3. Poll all THREE feedback channels (a GitHub "Request changes" / "Comment" review submitted with only a summary body lands in NONE of the comment endpoints, so the reviews channel is mandatory):
   - Reviews + decision: `gh pr view <pr_number> --json reviewDecision,state,mergedAt,latestReviews`. A review with non-empty `body` and `state` `CHANGES_REQUESTED` or `COMMENTED` is actionable feedback (channel `review`, key = review `id`).
   - Issue comments (channel `issue`): `gh api repos/<repo>/issues/<pr_number>/comments` (`<repo>` read from the state file, never hardcoded).
   - Inline diff comments (channel `inline`): `gh api repos/<repo>/pulls/<pr_number>/comments`.
   - **Filter by MARKER, never by author.** Skip any comment whose body carries `<!-- handled:...` (our own reply) or the CI preview marker (`publish.astro.preview_comment_marker`, when set). Do NOT filter by author login: a solo operator's own GitHub account is frequently the SAME account this automation posts and replies as, so an author-based filter would silently drop the human's own feedback along with the bot's.
4. For each feedback item not yet handled, process it. **Handled-detection is authoritative on the PR, not the local cache:** an item is already handled iff a bot reply carrying `<!-- handled:<channel>:<id> -->` already exists (scan inline-thread replies for `inline`; scan issue comments for `issue` and `review`). Use `handled_comment_ids` only as a fast-path skip; on a miss, confirm on the PR before acting.
   - **Classify intent and route it** per this table:

     | Comment intent | Routed to | Specialist action |
     |---|---|---|
     | Update/regenerate an image, a diagram is wrong, the featured image is off | `image-planner` then `image-builder` | Re-plan the `images.md` entry, then re-render (`remotion`/`ai-prompt` slots) or hand the human updated capture instructions (`screenshot` slots) |
     | Rewrite a section, the intro is weak, add a paragraph on a topic | `blog-writer` | Revise the affected part of the draft |
     | A claim is wrong or needs a source | `blog-researcher` then `blog-writer` | Verify/find the source, then rewrite with the citation |
     | Sounds robotic / off-voice | `blog-humanizer` | Humanization pass on the affected text |
     | Check something across the whole post | `blog-reviewer` | Scoped review; the editor acts on the findings |
     | Typo, single word, frontmatter tweak | editor inline | No subagent — delegation overhead isn't worth it |

     Ambiguous / large / risky (including a target this table doesn't cover cleanly): reply (with marker) asking ONE specific clarifying question, do not guess. Non-actionable (praise / answerable in words / approval remark): a brief marker-carrying ack, or skip.
   - **Route and act; the editor owns commit/push/reply.** Trivial items stay inline: edit the file under `$worktree/{content_dir}/` (or `$worktree/{assets_dir}/`) directly, re-derived from the item text (an idempotent target-state edit). Everything else is editor-orchestrated: dispatch the routed specialist subagent above with the comment text, the affected file path(s) under `$worktree/`, and enough context (slug, section) to act without re-reading the whole draft — the same dispatch-verify-route pattern the initial write uses for its own subagents. The subagent does only its craft (draft prose, image spec/render, sourced research, humanize pass, or scoped review) and hands the result back; it never touches git or the PR — the editor validates the returned output before proceeding (matches the ask, nothing else broke; a bad result re-spawns the same specialist once, a second miss falls back to a clarifying reply instead of guessing), then commits per the active adapter's `## On review-loop edit` (`${CLAUDE_PLUGIN_ROOT}/adapters/publish/<publish.adapter>.md`): `git -C "$worktree" add <path>`, commit, `git -C "$worktree" push` (re-triggers the staging deploy). **If the state file carries `wp_post_id` (the `wordpress-rest` adapter is active), after the push re-sync the WordPress draft by its stored ID** per that adapter's `## On review-loop edit` (re-convert the just-edited worktree copy to HTML, re-upload only changed media, POST to `/posts/<wp_post_id>` — never a second create). Then reply carrying the marker AND naming who did the work: "Addressed in `<sha>` via `<agent>`: <one line>. `<!-- handled:<channel>:<id> -->`" (inline/editor edits: "Addressed in `<sha>`: <one line>. `<!-- handled:<channel>:<id> -->`", no "via" clause).
   - Reply mechanics (every reply embeds the marker): inline comment, reply in its thread (`gh api -X POST repos/<repo>/pulls/<pr_number>/comments/<id>/replies -f body=...`); issue comment OR review-summary body, post an issue comment quoting/linking the original (`gh pr comment <pr_number> --body ...`).
   - Append `<channel>:<id>` to the local `handled_comment_ids` cache and persist (cache only; the on-PR marker is the at-most-once guarantee).
5. **`reviewDecision == APPROVED`, PR still open (not merged) — RECORD and HOLD, never finalize on this alone.** A GitHub review approval is advisory only: the merge (or an explicit console `approve`) is the action that authorizes finalize, this review by itself is not. If `pr-monitor.json` does not already carry `status: approved`, set it now, treat this firing as ACTIVE for §Adaptive cadence (the reviewer just acted), and report the approval as recorded-and-held. Do NOT run any finalize/archive bookkeeping and do NOT `CronDelete` — continue monitoring on the normal cadence exactly as `open` does; the reviewer may still leave more comments, or request changes, before the PR is actually merged.

   **PR found MERGED (`state == MERGED` / `mergedAt` set) — finalize requires proof of an explicit approval.** A merge can happen out-of-band from this monitor: most often the console's browser-Approve → merge → `resume <slug>` cleanup chain, a human merging their own GitHub-reviewed PR directly, or (rarely) a merge with no recorded review at all. Treat the merge as authorized to finalize when EITHER of these is true — **`{drafts_dir}/<slug>/approval.json` exists** (an explicit console/chat approve action) **OR `pr-monitor.json` already carries `status: approved`** (step 5 above already recorded a genuine GitHub review approval before this merge — the held state is now completed by the human's own merge):
   - **Either signal present** → treat this as an approved+merged finalize, NOT "closed outside this flow". Run the finalize-on-approval sequence (`${CLAUDE_PLUGIN_ROOT}/skills/blog-post-workflow/SKILL.md` Step 15.3 PR path, console-merge entry — the archive/bookkeeping/`mv` → `_archive` completes BEFORE this session returns), then `CronDelete` and exit.
   - **CLOSED without merge, OR MERGED with NEITHER signal present** → this is a genuine out-of-band close/merge that never went through a recorded Gate 2 approval: set `status=closed`, `CronDelete`, report — do NOT finalize (no proof-of-approval, so no archive/bookkeeping).
6. Otherwise set `last_poll=<now>`, apply §Adaptive cadence below, and exit; the next firing continues.

## Adaptive cadence (idle backoff)

Polling every 15 minutes is only worth paying for while a human is actually reviewing. Two state fields drive the backoff — `poll_interval_minutes` and `idle_polls` — both optional in older state files; treat a missing field as `15` / `0` and write both back on the first update.

- **This firing was ACTIVE** (it processed at least one new feedback item in step 4, handled a console comment, or recorded a fresh GitHub approval in step 5): set `idle_polls=0`. If `poll_interval_minutes` > 15, the reviewer is clearly back — set `poll_interval_minutes=15` and re-create the cron at 15 minutes (`CronDelete` this cron, then `CronCreate` with the identical prompt).
- **This firing was IDLE** (nothing new on any channel): increment `idle_polls`. When `idle_polls` reaches 4 AND `poll_interval_minutes` < 60: double `poll_interval_minutes` (15 → 30 → 60, hard cap 60), reset `idle_polls=0`, and re-create the cron at the new interval (`CronDelete` this cron, then `CronCreate` with the identical prompt).

Net effect: a PR under active review is polled every 15 minutes; a PR left overnight decays to hourly checks after ~3 idle hours instead of burning a firing every few minutes. The terminal exits (finalize on a proven merge, external publish, an unproven closed/merge, terminal `status`) are unaffected — they `CronDelete` regardless of the current interval, and the §Safety stops cutoff still applies. Recording `status: approved` (step 5) is NOT one of those exits — it only resets the idle backoff, per this section.

## Console comments (parallel channel)

When the user types a comment in the Claude console, handle it live in-session with the same classify-then-route path as step 4 (specialist dispatch for image/prose/sourcing/voice/review changes, inline only for trivial edits, editor owns the commit/push/reply naming the agent) — also via `git -C "$worktree"` with edits under `$worktree/`, and the same `wp_post_id` re-sync when the wordpress adapter is active. Console comments are one-shot turns (no re-polling), so they need no id dedup; they update the same branch (in the worktree) and state file. The cron fires as a wake-up (never truly concurrent with a live turn), so no locking is needed; the routine is idempotent regardless.

## Dedup invariant (crash-safe, at-most-once)

Reply at most once per `<channel>:<id>`. The guarantee does NOT rely on local write-ordering (a crash after replying but before persisting the cache would otherwise re-reply). Instead: every reply embeds `<!-- handled:<channel>:<id> -->`, and the authoritative pre-action check is whether that marker already exists on the PR. The content edit is idempotent (re-derived target-state), and the WordPress re-sync is idempotent too (update by stored ID, never create), so a crash after push but before reply is also safe.

## Safety stops

`CronDelete` on: finalize (a merge with proof of approval, or an external-publish detected — step 2 above; `wordpress-rest` only — counts as an approval for this purpose), a genuine out-of-band close/merge (no proof of approval), or an already-terminal `status` (`done` / `closed`). A bare `reviewDecision == APPROVED` is NOT a stop condition — it records `status: approved` and keeps polling (step 5). Bounded guard: if the PR has been open beyond a generous cutoff (compare `created_at` to now), auto-stop + report rather than poll forever.
